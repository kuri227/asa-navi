# 朝ナビ：通学ルート入力を楽にする案

段階Aの入力補助を実装済み。対象は通学ルート設定で編集中の区間。端末内の下書きから候補を出し、選ぶとその入力欄に反映する。

## スマホでの使い方

1. 最初に「出発地」「到着地」だけを入力。候補には駅名だけでなく路線・地域も出して、同名の駅を区別する。位置情報の許可は必須にしない。
2. 「候補を見る」で最大3件。最速だけを推さず、「乗換が少ない」「徒歩が短い」を必要に応じて並べ、所要時間・乗換数・徒歩時間・到着条件を同じ位置で比較できるようにする。前夜の利用なら曜日・到着時刻が変わると経路も変わることを明示する。
3. 「この経路で編集」を選ぶと、今の徒歩・電車・バスの区間フォームに下書きとして入る。「この経路ではない」場合は、別候補を選ぶか「この駅を経由」「バスを使わない」などを指定し直す。保存までは既存ルートに上書きしない。
4. 提案なし・圏外・タイムアウトでも「手入力」が使える。自動判定は警告に留め、たとえば前の区間の終点と次の始点が違う場合は「区間のつながりを確認」と表示する。出口の違いや徒歩連絡があるため、候補を勝手につなぎ直さない。

## 実装するならこの順番

| 段階                  | 試すこと                                                                                            | 判断基準                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| A: ローカル入力補助   | 前の区間の終点を次の空欄の始点に提案。入力中は、同じフォームですでに入力した名称から最大3件を表示。 | 候補は任意。選択後も編集でき、区間の境目の名前が異なっても保存できる。                                      |
| B: 候補UIの試作       | 架空データを返すProviderで、出発地・到着地→候補比較→下書き確認を検証する。                          | 小型画面で候補の違いを説明でき、拒否・再検索・手入力で詰まらない。実データを送信しない。                    |
| C: 実データの比較検証 | 対象地域・利用路線を決め、駅検索、徒歩接続、鉄道・バスの到着時刻指定を同じ試験ケースで比較する。    | 対象地域のカバー率、時刻表の鮮度、遅い通信・圏外時の復帰、表示/保存の規約、費用上限を満たしてから導入判断。 |

候補用の照合では全角英数字と半角英数字、大文字と小文字を同一視し、前方一致を優先する。選択時は入力された元の名称を使う。過去に保存した別ルートの名称検索と、区間のつながりに関する警告は今後の候補。

## バックエンドにする場合の境界

- Application側で場所検索と経路検索のProviderを分離する。前者は曖昧な文字列を候補へ、後者は選択した地点と希望到着時刻を比較できる経路へ変換する。結果は既存フォームが扱う順序付きの区間へ正規化し、Planning Engineは外部APIを参照しない。
- メーカーのAPIキーや利用量制限が必要なら、キーはサーバー側だけで保持。最小限の検索条件のみ送信し、出発地・到着地（自宅を含み得る）をアプリのエラーログや分析ログへ残さない。候補のキャッシュは利用規約が許す範囲に限る。確定した経路を保存してオフライン利用する設計も、Providerごとの保存条件に従う。
- 検索中に入力が変わったら古い結果を採用しない。出典、到着条件、取得時点、概算か時刻表ベースかを区別する。APIが落ちても手入力と既存ルートには影響させない。

次は架空の区間データで候補比較を試す。その後、1地域に絞り、同梱できる駅・停留所一覧の有無を先に調べる。実経路の比較には、徒歩＋鉄道、鉄道＋バス、同名駅、休日、到着時刻指定の5ケースを使う。

Cに進むときは、無料枠と超過時の費用、登録・カード要否、商用条件、再表示・保存・クレジット表記、レート制限、データ更新、サービス終了時の代替を公式資料で再確認してADR化する。新規契約や有料サービスの利用はユーザー確認後に行う。
